零 extern · 可独立测试 · 接口清晰

Problem

car_control.c 通过 extern 直接读取 5 个外部模块的全局变量，每个 extern 都是一条跨模块泄漏路径，无法独立测试。

Solution

将 Car_ControlLoop 签名改为接收 struct 参数（sensor inputs），返回 struct 输出（target speeds）。main.c ISR 负责组装输入、分发输出。

Wins

  • locality: 控制逻辑集中一个模块
  • leverage: 一个 struct 入参，一对速度出参
  • 接口缩小 80%：5 extern → 1 参数结构体
  • car_control 可在 PC 上单测

2. count 双写竞争 —— 事件队列替代共享计数器

ISR 和 task 状态机同时写 count，__disable_irq 保护是脆弱信号

Worth exploring in-process
main.c (TIM6 ISR)task.c (5 tasks)yaw_track.c

Before — 双写竞争

  ISR[TIM6 ISR 丢线边沿检测]
  TASK[task 状态机 YawTrack 弯道完成]
  CNT[count 变量]
  DB[count_debounce]
  ISR -->|++ 无锁| CNT
  TASK -->|++ __disable_irq| CNT

  TASK -->|写| DB
  CNT -->|读| SM[Task 状态机 switch/case]
  style CNT fill:#fef2f2,stroke:#dc2626,stroke-width:2px
  style DB fill:#fef2f2,stroke:#dc2626

两个不同事件源驱动同一计数器，语义混乱

After — 事件队列

graph TD
  ISR2[TIM6 ISR]
  TASK2[task 状态机]
  EQ[(事件队列 FIFO)]
  SEQ[SegmentSequencer]
  SM2[Task 状态机 switch]
  ISR2 -->|push LINE_LOST| EQ
  TASK2 -->|push CURVE_DONE| EQ
  EQ --> SEQ
  SEQ -->|advance_segment| SM2
  style EQ fill:#0f172a,color:#fff
  style SEQ fill:#0f172a,color:#fff

单一写入者 · 事件语义明确 · 无需关中断

Problem

count 被 ISR（丢线边沿）和 task 状态机（YawTrack 弯道完成）两个异构事件源同时写入，__disable_irq() 是代码中的"危险信号"。

Solution

引入 SegmentSequencer 模块：ISR emit LINE_LOST 事件，task emit CURVE_DONE 事件，Sequencer 消费事件并推进段编号。count 退化为只读推导值。

Wins

  • locality: 段推进逻辑集中一处
  • 删除 __disable_irq / __enable_irq 对
  • 事件语义自文档化
  • count_debounce 与 Sequencer 合并

3. angle_normalize 重复 —— 提取共享工具模块

同一逻辑两份实现：car_control.c:41 和 yaw_track.c:111

Strong in-process
car_control.c:41-45yaw_track.c:111-112

Before — 两份重复实现

car_control.c 
while (diff >  180) diff-=360;
while (diff < -180) diff+=360;
yaw_track.c 
while (delta >  180) delta-=360;
while (delta < -180) delta+=360;

修一处忘另一处 → bug

After — 共享模块

angle_utils.h 
float Angle_Normalize(float diff);
car_control.c 调用 yaw_track.c 调用

一处修改，所有调用者受益

Problem

±180° 归一化逻辑在 car_control.c（static）和 yaw_track.c（内联）各实现一次。修改必须同步两处，否则漂移。

Solution

新建 angle_utils.c/h，导出 Angle_Normalize(float) → float。car_control 和 yaw_track 均改为调用此函数。

Wins

  • DRY: 1 份实现，2 个调用者
  • leverage: 归一化算法一处维护
  • 零依赖（纯计算，仅需 math.h float）
  • 可独立单元测试

4. car_control 两层 API 约定脆弱 —— 合并模式入口与微调

Car_StartLine（重置 filter）vs Car_SetSpeed/SetTargetAngle（不重置）— 纯约定，无强制

Worth exploring in-process
car_control.c (全部 9 个公开函数)task.c (5 个 Run_Task 调用者)

Before — 两层 API，约定驱动

Car_StartLine(θ, v, ff) ← 重置 turn_out_smooth
Car_SetSpeed(v) ← 不重置
Car_SetTargetAngle(θ) ← 不重置
Car_SetFFDiff(ff) ← 不重置
❌ 调用 Car_SetSpeed 误代 Car_StartLine = filter 崩塌

After — 统一入口 + 不可变段配置

Car_EnterSegment(SegmentConfig cfg)
SegmentConfig = {angle, speed, ff_diff, mode}
✓ 一次调用设置全部参数
✓ 段内不可变 → 无需微调 API
✓ filter 行为由 mode 决定，不依赖调用者记得

Problem

car_control 暴露 6 个写 API（StartLine/StartStraight/TurnTo + SetSpeed/SetTargetAngle/SetFFDiff），两级调用约定靠注释传递，无编译期约束。

Solution

合并为 Car_EnterSegment(SegmentConfig)，结构体包含 {mode, angle, speed, ff_diff}。段内无需微调的场景（Task1/2/5）一行搞定。Task3 刹车策略用单独接口。

Wins

  • 接口缩小: 9→4 公开函数
  • 不可能"忘调 Car_StartLine"
  • leverage: 一个 struct 表达完整段意图
  • 调用约 30 行样板代码消失

5. Task 4 的 29 状态三圈重复 —— 参数化循环替代复制粘贴

3 圈 × 7 段 = 21+ 个几乎相同的 case，仅有 angle 微调 ±2°

Worth exploring in-process
task.c Run_Task_4 (case 0–28, ~290 行)

Before — 29 状态手写展开

case 0–7: 第一圈   angle=-38/0/-146/180
case 10–17: 第二圈   angle=-34/0/-148/180
case 20–28: 第三圈   angle=-37/0/-146/180
每圈 7 个状态，仅有 target_angle 微调 2°~4°

After — 参数化循环 × 圈数

const float lap_angles[3][4] = {
  {-38,   0, -146, 180},  // lap 1
  {-34,   0, -148, 180},  // lap 2
  {-37,   0, -146, 180},  // lap 3
};
current_state = (lap * 7) + segment;
290 行 → ~40 行

Problem

Run_Task_4 展开 29 个状态（3 圈 × 7 段 + 停车），每圈仅有 target_angle 微调 2°，修改一个段需要同步 3 处。

Solution

用 lap_angles[3][4] 查找表 + 周界状态机 = lap*7+segment 计算 current_state。段推进逻辑提取为函数，复用于每圈。

Wins

  • locality: arena 参数集中一个数组
  • 290 行 → ~40 行 (86% 缩减)
  • 改角度只需改数组一个元素
  • 增加圈数不增加代码行

7. Encoder 读即清零 —— 隐藏契约未文档化

调用者必须知道 Encoder_Get_Count 有破坏性副作用，接口未表达

Speculative in-process
encoder.cmain.c ISR

Before — 破坏性读取，隐含契约

int16_t Encoder_Get_Count_Left(void) {
  cnt = __HAL_TIM_GET_COUNTER(&htim2);
  __HAL_TIM_SET_COUNTER(&htim2, 0);  ← 清零！
  return cnt;
}
读两次 = 第二次返回 0 · 无类型/命名提示

After — 语义明确的接口

int16_t Encoder_ReadAndReset(EncoderCh ch);
// 名字自文档：读 + 清零一步完成
或拆为两步：
int16_t Encoder_Read(EncoderCh ch);
void    Encoder_Reset(EncoderCh ch);

Problem

Encoder_Get_Count 读后立刻清零计数器。函数名暗示纯读，实则破坏性操作。调用者若不知此契约则会出错。

Solution

重命名为 Encoder_ReadAndReset()，语义自文档化。或拆分为 Read + Reset 两步，让调用者显式管理清零时机。

Wins

  • 接口名 = 行为契约
  • 消除"我不知道会清零"类 bug
  • 零运行时开销
